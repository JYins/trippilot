# TripPilot｜途行智驾

开车时说一句话，座舱 Agent 把它拆成多步任务：查路线、看天气、问限号、设提醒、调车内设备；该拦的先拦，该确认的先确认，还会记住你的长期偏好。

TripPilot 是一个面向北京出行场景的语音优先座舱 Agent 原型。它关心的不只是“模型能不能答”，而是一次任务有没有被正确拆开、工具有没有按顺序执行、安全边界有没有守住、最后的结果能不能被逐项验证。

目前项目有：

- 15 条从真实行程整理出的体验场景，起点统一为北京阜通站；
- 33 条面向真实北京出行任务的 trajectory eval 用例，当前 **27/33** 通过；
- **166** 项自动化测试；
- 导航、天气、提醒、行程记录、媒体、车控、限号、地域知识等工具能力；
- Qdrant 本地偏好记忆与 BGE 中文语义召回；
- 一条从意图识别、信息澄清、任务规划、安全判断到执行验证的完整轨迹。

## 这东西是干嘛的

TripPilot 想处理的是开车时那些“一句话里其实有好几件事”的请求。

比如：

> 明天中午从望京去国贸面试，结合天气看几点出发，再提前两小时提醒我。

这不是一次普通问答。Agent 要先理解目的地和时间，再查路线、查天气、估算出发时间，最后创建提醒。前几步是读取信息，最后一步会产生副作用，所以不能把它们当成同一种操作。

再比如：

> 有点热，空调开大点，顺便把天窗打开，音量调小点。

一句话会被拆成空调、天窗和媒体三个动作。demo 里的车控状态是纯软件模拟，但任务拆解、权限判断、工具调用和结果验证走的是同一条 Agent 链路。

还有一些请求，好的答案不是立刻执行：

> 带我去 798。

798 有多个入口。如果系统没弄清用户要去哪一侧，就不该先猜一个终点，再用一条看起来完整的路线掩盖错误。TripPilot 会把“该不该追问”也当成产品能力来评测。

### 15 条真实行程里有什么

这组场景来自北京的实际出行表达，起点统一为阜通站，包含：

- 去 798、三里屯、菜市口、亦庄、中关村、学院路和机场；
- 去潮白河前先看天气，再决定是否出发；
- 查询“还有多远”“几点能到”这类在途问题；
- 去菜市口或三里屯前先问当天限号；
- 规划约 350 公里的乌兰察布长途行程；
- 换歌、调音量、开空调、开天窗；
- 问“798 为什么叫 798”这类地域知识；
- 用“去那个河边”测试系统会不会在信息不足时乱猜。

原始的 15 条行程进入评测集后，其中一条连续在途任务被拆成 4 个可单独检查的回合，因此形成了 18 条真实场景用例；再加上已有的安全、记忆、恢复和幂等用例，完整数据集是 33 条。

### 现在能调哪些工具

- **地图与天气**：查路线、距离、时长、到达时间和天气；
- **提醒与行程记录**：创建提醒，重复提交时做幂等去重；
- **`media` 媒体**：换歌、调节音量；
- **`vehicle` 车控**：调空调、开关天窗，全部是纯软件模拟；
- **`restriction` 限号**：读取版本化的北京限行录制数据；
- **`knowledge` 地域知识**：只回答知识库里核实过的内容，查不到就明确说不知道。

后四类工具已经补齐。这里有个很实际的取舍：知识问答目前宁可覆盖少，也不让模型现场补一个貌似合理的答案；限号也宁可标明数据日期，不把历史快照说成实时政策。

## 为什么做它

TripPilot 不是从一张空白架构图开始的。做前几个项目时积累下来的问题，刚好在座舱 Agent 里碰到了一起。

### Coval：Agent 得记住人，而不只是记住这一轮

做 Coval 的长期记忆时，一个很直接的体会是：如果系统每次都把用户当陌生人，很多“智能”只是重复询问。

所以 TripPilot 用 Qdrant 本地文件保存偏好。像“高速优先”“常去首都机场 T3”这样的长期信息可以被语义召回，下一次规划时进入上下文。

但记忆不是越多越好。家庭住址等敏感内容不能因为模型觉得“以后可能有用”就直接落盘，因此又加了 Memory Gate：普通稳定偏好可以写入，瞬时行程不当长期偏好，敏感候选必须先得到用户确认。

### RAG 检索评测：指标好看，不等于真的有用

做 RAG 检索评测时，对“总分很好看，但真正关心的问题没有被检查”这件事会格外敏感。

这直接影响了 TripPilot 的 eval：每条用例都写清 `success_criteria`，runner 必须逐项执行对应断言。数据里写了“提醒已创建”，就真的检查提醒；写了“没有瞎猜目的地”，就真的检查轨迹，而不是只看程序有没有跑完。

项目早期确实出现过一次假绿：评测集读到了 `success_criteria`，却没有真正执行它。修完之后，未知标准会直接失败，不能静默跳过。现在看到 27/33，比一个含糊的“整体表现不错”更有信息量。

### V2V 多智能体协同（一作）：一句话背后是拆解与协同

V2V 多智能体协同里，任务拆解、角色分工和结果汇合本来就是核心问题。放到座舱里，planner 做的是同一类工作：把一句话拆成地图、天气、提醒或车控等步骤，再组织它们的先后关系。

重点不在“接了多少工具”，而在工具之间有没有清楚的边界。天气查询失败时，路线结果不该凭空消失；创建提醒需要确认时，读取天气不该被一起误判成高风险操作。

### Qwen LoRA 微调：模型行为要可控，也要能验证

做 Qwen LoRA 微调时形成的另一个判断是：模型行为可以被改善，但不能因此把关键安全结论交给概率输出。

所以 TripPilot 让模型负责理解和规划，让确定性程序负责安全判定。身份权限、敏感记忆、工具结果注入检查、拒绝与确认，都不靠 LLM 猜。这样做少了一点“全都交给模型”的简洁，却换来了可复现、可解释和可回归。

## 一轮请求是怎么走的

可以把 TripPilot 理解成一条带检查点的任务流水线：

1. **理解意图**：用户是在导航、查天气、设提醒，还是同时做几件事；
2. **召回偏好**：从本地记忆里找与当前请求相关的长期偏好；
3. **信息澄清**：地点或语音信息不够时先追问；
4. **任务规划**：把一句话拆成有顺序的工具步骤；
5. **安全判断**：逐项给出 allow、deny、degrade 或 confirm；
6. **工具执行**：调用地图、天气、提醒、媒体、车控等能力；
7. **结果验证**：检查工具是否成功、目标是否完成；
8. **失败恢复**：在可恢复的错误上重试，并把过程留在 trajectory 中。

trajectory 不只是给 demo 做动画。它保留一轮请求真正走过的节点、策略结论和工具结果，让“系统为什么这么做”可以被检查，也让评测能够对过程下断言，而不是只盯着最后一句话。

## 它怎么做判断

这里最重要的一条学习笔记是：**语言模型适合处理模糊语义，不适合当安全开关。**

### Policy Gate 是确定性程序

`policy_gate` 不调用 LLM，它依据明确规则判断：

- **ABAC 身份与上下文**：用户是已认证车主还是其他角色，车辆处于驻车还是行驶模拟状态；
- **Memory Gate**：候选信息是瞬时内容、普通偏好还是敏感信息；
- **低置信度保护**：语音识别置信度不足时，副作用操作不能直接执行；
- **注入检查**：工具返回的文本先经过检查，异常内容不会被当成后续指令；
- **未知能力默认拒绝**：没有登记的工具不会因为模型生成了一个名字就被执行。

判定结果也不是只有“能”或“不能”：

- `allow`：直接执行；
- `deny`：立即短路，不再偷偷换一条路径执行；
- `degrade`：例如行驶中减少选项，降低交互负担；
- `confirm`：对有副作用或涉及敏感信息的动作，先等用户明确确认。

deny 之所以直接短路，是因为“拒绝以后继续让 planner 想办法”很容易把安全规则变成一道可绕过的建议。

### 确认不是一个布尔按钮

早期如果只让客户端回传“我确认了”和候选正文，客户端就有机会在确认时替换内容。现在的确认协议是：

1. 服务端保存待确认动作的快照；
2. 返回一个一次性随机 nonce；
3. 客户端确认时只提交 nonce，不重新提交候选正文；
4. nonce 与同一会话、同一待确认对象绑定，消费后立即失效；
5. 审计轨迹用 `confirm_id` 对上“确认了什么”和“最终写入了什么”。

因此，伪造正文、重复使用 nonce、拿工具确认去替敏感记忆放行，都会被拒绝。当前原型的待确认快照保存在单进程内存里，进程重启后需要重新发起确认；这也是后面要补持久化的地方。

## 偏好记忆：为什么换成 BGE

偏好记忆最初使用 FastEmbed 的默认英文模型 `bge-small-en-v1.5`，但实际输入几乎全是中文口语。这种错配在“去机场”召回“常去地点：首都机场 T3”时暴露得很明显：字面不一样，英文模型容易漏掉中文语义关系。

现在默认 embedding 已换成 `BAAI/bge-small-zh-v1.5`，由 sentence-transformers 在本地运行，向量保存在 Qdrant 本地文件中。

在 21 条中文 probe 上：

| 模型 | recall@3 | 结果 |
|---|---:|---|
| 原 FastEmbed 默认英文模型 | 0.857（18/21） | “去机场”等中文改写会漏召回 |
| BGE `bge-small-zh-v1.5` | **1.000（21/21）** | 21 条全部命中 |

这个变化的意义不是把小数点刷得更漂亮，而是让“Agent 记得用户常去 T3”在用户换一种说法时依然有效。

代价也很清楚：BGE 依赖更重，首次使用需要下载模型，冷启动比原方案慢；向量维度从 384 变成 512，旧的本地 collection 不能直接混用。对于当前几十条偏好的单用户原型，召回正确性比省下这点冷启动更重要。

## 评测怎么做

TripPilot 的评测对象不是一句回答，而是完成任务的整条 trajectory。

`fixtures/dataset_v0.jsonl` 里有 33 条任务。每条都包含输入、上下文、允许使用的工具、必须经过的节点、禁止动作，以及可执行的 `success_criteria`。

一次评测会关心这些问题：

- 该澄清的时候，是否真的经过 clarify；
- deny 以后，工具是否真的没有执行；
- 行驶状态下，复杂交互是否按规则降级；
- 创建提醒前，是否经过了对应确认；
- 敏感记忆确认的对象，是否就是最后写入的对象；
- 工具失败后，恢复路径是否出现且最终验证成功；
- 重试有没有造成重复提醒；
- 用户要求的每一项结果，是否都有确定性断言。

### “读了标准”不等于“检查了标准”

这是这个项目最值得留下的一条评测笔记。

早期 runner 会读取每条数据里的 `success_criteria`，但没有逐项执行。于是轨迹走完就可能显示 PASS，即使“提醒创建成功”或“目的地已更新”根本没人检查。这类绿没有意义。

现在每个 criterion 都必须映射到一条确定性检查；不认识的 criterion 会直接标红。断言失败时，报告会指出是哪一项失败，而不是只给一个总分。

### DeepSeek judge 只提供建议分

DeepSeek judge 已经接入，用来观察两类很难靠规则完整描述的问题：

- 规划步骤是否合理、是否绕路；
- 澄清问题问得是否自然、是否抓住重点。

这些分数只进入报告，定位是 **advisory**，不参与通过门禁。原因很简单：LLM judge 适合提示“这里可能不自然”，却不适合裁定“敏感操作是否已经确认”。

真正决定 PASS / FAIL 的 deny、degrade、confirm、必经节点覆盖、禁止动作和逐项成功标准，全部由确定性程序判断。即使 judge 给出低分，也不会把本来正确的安全轨迹判失败；反过来，judge 觉得回答不错，也救不了一条漏确认的轨迹。

### 当前结果：27/33

33 条用例里有 27 条通过，6 条仍然是红的。这个数字保留了真实缺口，没有通过降低标准把它们抹平。

六条分别是：

- **TP-REAL-001**：用户说“带我去 798”，系统还缺少“798 有多个入口”的澄清知识，问不出南门还是北门；
- **TP-REAL-002**：用户说“去三里屯”，系统还不能高质量追问南区还是北区；
- **TP-REAL-008**：用户说“去机场”，系统还不能把首都机场 T2、T3 等选项问清楚；
- **TP-REAL-009**：约 350 公里的乌兰察布长途规划还没有“出发前必须确认”的策略；
- **TP-REAL-013**：“去三里屯，顺便看看限号”仍暴露三里屯分区澄清缺口；
- **TP-REAL-014**：系统会对“去那个河边”发起澄清，也不会瞎猜，但澄清答案还没有正确绑定回 `destination`。

前三条看起来都像“地点识别成功了”，但评测要求更高：知道“三里屯”这个词，不等于知道用户最终要去哪个可导航终点。

## 诚实边界

- **车况和车控是纯软件模拟。** 驻车、行驶、空调、天窗、音量等状态不来自真实车辆，也不控制真实车辆。
- **地图、天气和限号使用录制数据。** 它们用于稳定复现任务，不代表当前实时路况、天气或政策。
- **无 key 时使用确定性 stub。** 它能让主循环和 demo 离线运行，但它是可复现的演示后端，不代表真实模型的语言理解上限。
- **知识问答覆盖很小。** 当前只回答已经核实并写入录制知识库的条目；未命中时明确失败，不临场编答案。
- **部分播报类断言检查的是数据是否就位。** 例如 ETA、天气结论和休息点所需字段已经返回，不等于 stub 已经生成了理想的口语播报。
- **截图是真实运行结果。** 两张图来自本地后端实际执行，没有把概念稿当成产品页面。

这些限制不是免责声明式的小字，而是评估这个原型时必须一起看的事实。

## 已知局限

除了当前 6 条红项，还有几件没有被包装成“已经完成”的事：

- 多入口、商圈分区、机场航站楼等地点知识仍然稀薄，澄清质量受限；
- 真正的多轮连续行程评测还没完成，当前连续场景被拆成单轮用例检查；
- Gradio demo 展示了对话和轨迹，但还没有完整呈现所有敏感记忆确认交互；
- 待确认快照是单进程内存状态，重启会丢失，也不适合直接扩到多实例部署；
- 媒体和车控状态同样是进程内模拟，重启后会复位；
- BGE 首次加载有明显冷启动，后续若面向车端部署需要进一步压缩和优化；
- 当前地域知识库覆盖面很小，限号、地图和天气也都不是实时服务；
- DeepSeek judge 可能带有模型偏好，因此始终只作为观察信号。

## 路线图

下一阶段不急着继续堆工具，先补当前轨迹里最有价值的缺口：

1. 建立多入口、商圈分区和航站楼知识，让澄清能给出具体选项；
2. 为长途路线补充距离阈值、休息建议与出发确认策略；
3. 把澄清结果可靠地绑定回目的地，并补真正的多轮 trajectory eval；
4. 扩充地域知识库，同时继续坚持“查不到就不编”；
5. 把确认快照迁到可持久化、可多实例共享的存储；
6. 接入真实语音链路，评估车内噪声下的识别置信度与澄清体验；
7. 在不改变诚实边界的前提下，再接实时地图、天气和车辆接口。

TripPilot 现在还不是一套可以装进量产车的系统。它更像一份可以运行、可以追踪、也敢把失败写出来的座舱 Agent 学习笔记：模型负责理解世界，程序负责守住边界，评测负责证明两者真的配合过。
