# 偏好记忆过期策略：forget_expired 显式删除

日期：2026-10-08 ｜ 状态：已决策，代码已落地（store.forget_expired）

## 背景

forget 链路现状只有 forget()（按 id）和 forget_all()（按用户），
没有"很久没用的偏好怎么处理"。几百到几千条规模下，过期记忆是
召回噪音，也是隐私 hygiene（用户早忘了自己说过的偏好还躺在库里）。

约束：单进程原型，无后台调度器；删除是破坏性操作，必须是显式的。

## 候选方案

1. **forget_expired(older_than_days) -> int**：按 created_at 范围删除，
   返回删除条数，显式调用。代价：触发靠调用方（用户说"忘掉旧的"/
   显式运维），库不会自己变小。
2. **后台自动过期**（daemon/cron 定时扫）：代价：原型无常驻进程，
   接调度器是新复杂度；更大的问题是产品风险——半夜静默删用户记忆，
   用户早上发现偏好没了，无法解释。
3. **不做过期**（现状）：代价：库只增不减，过期偏好永久参与召回。

## 选择

方案 1。落点：PreferenceStore.forget_expired(older_than_days)，
用 created_at 的 DATETIME payload 索引做范围删除（Range lte），
返回删除条数；库不存在时返回 0（与 forget/forget_all 行为一致）。

## 为什么

**用 created_at 索引做范围删**：O(索引) 而不是全表扫描；这就是
20261008-vector-db-design.md 里给 created_at 建 DATETIME 索引的
直接理由——设计和实现闭环。

**不自动过期**：两个理由。工程上，单进程原型没有调度器，为过期接
cron/daemon 是新复杂度。产品上，删记忆是破坏性操作，必须由用户
亲口说"忘掉"或显式运维触发——静默删除用户数据，丢的是信任，
这比多几条过期记忆贵得多。

**返回删除条数**：调用方（和用户）能确认"删了 N 条"，诚实可验证；
删了 0 条也是有效信息（"没有 30 天前的记忆"）。

**诚实记下放弃的东西**：基于"最后召回时间"的 LRU 式过期——需要每次
recall 回写 access_at，写放大一倍；当前规模下 created_at 足够，
不为"更智能"付复杂度。也承认：older_than_days 的具体天数是产品决策
（30/90/180），API 只收参数不拍板，拍板留给调用它的产品逻辑。

## 对 eval 的影响

- 纯新增 API，无现有调用方；33 条回归零变化。
- 新增测试：一条 60 天前 + 一条现在，forget_expired(30) 返回 1，
  旧的消失、新的保留；再调返回 0。
