## 背景

API 原来接收客户端回传的 `pending_memory_confirms` 候选正文，`confirm=true` 后图会把这份正文当成上一轮已经过 Memory Gate 的候选直接写盘。审查时用“合法确认布尔值 + 伪造敏感候选”可以稳定复现越权写入；同时只回复“确认”的正常客户端没有上一轮候选，无法完成写入。约束是保持 `graph.py` 的确定性门禁流程不变，且原型仍是单进程内存会话，不把 eval runner 改成走 API。

## 候选方案

1. 继续回传候选正文，再加 SHA-1 让客户端一并提交；代价是摘要和正文都能被攻击者重算，不能建立可信边界。
2. 用服务端密钥给候选正文签名，客户端回传正文和签名；可以防篡改，但正文仍有第二条输入路径，密钥轮换、序列化一致性和多候选签名都增加了当前原型不需要的复杂度。
3. 服务端按 session 保存候选快照，客户端只回一次性随机 nonce；代价是进程重启会丢失待确认项，多进程部署前还需要把快照迁到共享存储。

## 选择

选择方案 3。每个待确认候选用 `secrets.token_urlsafe(24)` 生成 nonce，服务端保存候选副本；响应只给 nonce、展示正文和正文的 SHA-1 摘要。确认请求模型删除候选字段，只接受 `confirm_nonce`。消费 nonce 时在锁内先取出并删除，未知、重复或缺失 nonce 都返回 400。

## 为什么

先写了四个 API 回归用例：旧实现既没有快照容器，也会接受伪造候选，测试如预期失败。方案 1 看起来改动最小，但试着沿攻击链推演后发现攻击者可以同时替换正文和摘要，SHA-1 在这里最多用于日志或界面核对，不能承担认证。方案 2 能成立，但会继续保留“客户端提交待写正文”这个容易误用的接口。服务端快照让可信数据只有一个来源，图只收到 API 恢复的候选，边界更直白。24 字节随机 nonce 对本地原型已经足够，且不把摘要算法误当安全机制；锁是为了让并发的两个相同确认只有一个能消费成功。接受的代价是待确认状态暂不持久化、没有超时清理，进程重启后用户需要重新发起记忆请求。

## 对 eval 的影响

新增 `tests/test_api_confirm.py`，固定检查伪造候选无法写入、nonce 重放拒绝、空确认明确报错，以及正常两轮确认成功。现有 `eval/eval_runner.py` 直接构造图状态，不经过 API，因此评测数据和断言不变；后续若 eval 覆盖 HTTP 多轮轨迹，应把 nonce 与同一 session、同一候选摘要的关联和一次性消费列为回归项。
