# 决策：Gradio demo 壳的交互与轨迹展示

## 背景

免费部署已经在 `20261008-deploy-gradio-free.md` 里定为 HF Gradio Space，这次要补的是
展示壳，不能改冻结的 agent 主线。当时看到 `web/index.html` 已经有完整的节点摘要逻辑，
也看到 Gradio 6.29.1 的 `Chatbot` 使用 messages 数据格式，因此问题集中在怎样忠实搬运
轨迹、怎样保留多轮 session，以及怎样控制部署文件位置。

## 候选方案

1. 只用 Chatbot 展示回答和轨迹：代码最少，但轨迹会混进对话，节点状态与执行次序不清楚。
2. 用多个 Gradio 原生组件逐节点拼时间线：组件语义直白，但十个节点会带来大量重复组件和
   显隐事件，更新链路容易漏字段。
3. 用 `gr.HTML` 输出 `<details>` 时间线：Python 一次生成静态、安全转义的摘要，能保留
   点击展开，同时代价是这块展示不具备 Gradio 原生组件的独立事件能力。

## 选择

选择方案 3。主链路和辅助节点各自成组；组内先按 `visited_nodes` 的真实执行顺序排列并标注
“第 N 个”，未经过的节点置灰放到组尾。会话标识放在 `gr.State`，每次调用把后端返回的
`session_id` 写回。`needs_user_input` 只在回答后提示用户继续输入，不实现 confirm nonce 的
完整往返界面。部署依赖固定为本机实际导入成功的 `gradio==6.29.1`。

## 为什么

当时最纠结的是 HTML 会不会显得不够“原生”，但实际需要的是十个节点、三种状态和多条事件
摘要；`<details>` 正好提供无 JavaScript 的展开行为，比纯 Chatbot 清楚，也比拼很多原生组件
容易保持与 `web/index.html` 一致。执行过的 chip 按 `visited_nodes` 排，是因为源码声明顺序只
代表设计图，不能冒充本轮真实顺序；未走过的仍放组尾，方便看出被跳过的环节。

完整 confirm UI 需要保存并回填 nonce，还要区分澄清与敏感记忆确认，这已经接近新增产品
行为；本次只做部署壳，所以拍板显示明确的继续输入提示，接受不能一键确认的代价。`gr.State`
不会把 session id 暴露成用户输入，又能让“还有多远”沿用同一会话，比全局变量更适合多个
浏览器会话。版本号没有追新或猜测，直接采用本机 `.venv` 已安装且 import 成功的 6.29.1，
减少本地验收与 Space 构建的差异。

Space 的默认 Gradio 构建约定从仓库根目录读取 `app.py` 和 `requirements.txt`，所以部署时
需要把两个 demo 文件改名放到根目录；仓库内仍保留 `demo/` 隔离部署依赖，避免 Gradio 进入
主项目依赖。这个做法多了一步复制改名，但守住了主线冻结和简历白名单边界。

## 对 eval 的影响

Gradio 壳不进入 eval，也不新增 agent 行为、工具或 trace 字段。主测试配置仍只收集
`tests/`；`demo/test_gradio_smoke.py` 只在显式调用时验证 import 和 Blocks 构造，不启动
服务、不调用 `turn()`，也不会触发偏好记忆或 BGE 下载。
