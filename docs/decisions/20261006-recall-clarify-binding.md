## 背景

审查 blocker #7、#8 指出了两条会让主流程“看似接上、实际没生效”的链路。`memory_recall` 已经把偏好放进 state，但 planner 从未看到它；`clarify_answer` 则只要非空就能清除地点歧义，而且 planner 仍可能拿旧 destination 查路线。约束是模型只应看到规划所需的最少偏好字段，地点消歧必须由确定性程序完成，不能让 LLM 猜。

## 候选方案

1. 把完整 Preference 和原始澄清答案都交给 LLM 判断：改动少，但会暴露 id、user_id、时间等无关字段，消歧结果也不稳定。
2. planner 只接收 `kind/content`，澄清节点用确定性名称规则绑定选项：多写一点规则和反例测试，但输入边界清楚、可审计。
3. 澄清只接受标准名精确匹配：最保守，但用户说“西站”而选项是“北京西站”时体验生硬。

## 选择

选择方案 2。偏好上下文固定为最多 3 条 `[{"kind": ..., "content": ...}]`，明确排除存储 id、user_id、created_at 等元数据。地点先做去除首尾空白后的标准名精确匹配；没有精确命中时允许答案与标准名互相包含，但必须唯一命中。成功后把标准名同时写入 `clarify_resolved` 和 `destination`；零命中或多命中都继续追问。

## 为什么

工作日志：召回本来已经限制 `top_k=3`，因此 planner 沿用这个上限，不再引入第二套阈值。实际检查 Preference 字段后，规划只需要类别和正文；其余字段既不改变路线选择，也扩大了模型可见面，故删掉。消歧一开始考虑过任意包含命中，但“西站”可能同时命中“北京西站”和“西站地铁站”，如果取第一项仍然是在猜，所以最终定为“精确优先、包含关系仅限唯一命中”。代价是某些仍有歧义的短回答会多问一轮，但这比带着错误目的地执行路线查询安全。匹配成功覆盖 destination，而不是只记一个旁路标志，确保 planner 与 Policy Gate 使用的是同一个选择结果。

## 对 eval 的影响

新增 `tests/test_graph_recall_clarify.py`：用 recording LLM 直接断言 planner 收到脱敏偏好；覆盖合法简称唯一命中后 destination 更新且路线继续执行；覆盖无关回答仍停在澄清节点且 `map.route` 零执行。原有 DeterministicStub 不读取 preferences，既有确定性规划行为保持不变。
