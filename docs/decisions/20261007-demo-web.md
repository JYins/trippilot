# 决策：在线体验 demo 的前端与部署方案

日期：2026-10-07
背景：用户要一个"别人点开链接就能直接体验"的在线 demo，用途是简历/面试外发。
约束：① 技术选型只用简历白名单（AGENTS.md 第 7 节），白名单外依赖需决策记录+用户批准；
② AGENTS.md 目录约定已写死 `web/ # 最小控制台，不搞前端工程`；
③ 诚实边界：车况纯模拟、地图/天气走 recorded fixtures，demo 里必须明示；
④ `trippilot/llm.py` 默认是 DeterministicStub——无 key 可跑，这是部署可行性的关键。

## 候选方案

### 前端

1. **Gradio**：Python 一把梭，HF Spaces 一键部署。代价：① 新依赖，白名单外，需用户批准；
   ② 聊天 UI 定制弱，trajectory 时间线这种"看 agent 怎么想"的展示不好做，而这正是面试卖点；
   ③ 长得像每个教程 demo，没有"这是我设计的"味道。
2. **React/Vue 前端工程**：代价：白名单外、重、为一个小控制台不值；且 AGENTS.md 明确"不搞前端工程"。
3. **手写最小 HTML/CSS/JS 控制台，FastAPI 挂 static**：零新依赖（FastAPI 已在白名单，
   手写页面不算依赖引入）；正好落实 AGENTS.md 既定方向；trajectory 时间线、场景快捷按钮
   这种定制展示反而最好做。代价：手写，样式上限看写的人；但"最小控制台"的定位下够用。

### 部署

1. **Hugging Face Spaces（Docker）**：免费；FastAPI 原样跑；DeterministicStub+fixtures
   意味着镜像里无 key、无外部调用，冷启动快、不烧钱。代价：需要用户自己的 HF 账号建 Space；
   国内访问速度一般（面试官多在国内，实测后再看）。
2. **Railway/Render 免费 tier**：代价：休眠唤醒慢、免费额度小，不如 Spaces 稳。
3. **只发静态页**：代价：跑不了 Python 后端，demo 只剩壳，失去意义。

## 选择

前端选 3（手写最小控制台），部署选 1（HF Spaces Docker）。

## 为什么

- 零白名单外依赖：不需要为前端开"简历外技术"的口子，面试官按简历问的时候，
  仓库里每一项都能对上（FastAPI/LangGraph/Qdrant 全是简历原话）。
- demo 的核心卖点不是"界面漂亮"，是**看得见的 trajectory**：
  用户输入一句话，页面同时展示 agent 走过的节点（intent→clarify→planner→
  policy_gate→tool_executor→verifier）和最终播报——这正是我们 trajectory eval
  在测的东西，demo 和评测用的是同一套 trace。
- 场景快捷按钮直接用 15 条真实行程用例的原话（去798/今天限号吗/换首歌…），
  点一下就是一条可复现的 eval case，demo 即广告。
- 诚实徽章：页面常驻"座舱状态·模拟 / 地图天气·录制数据 / 无需真实车辆"，
  和 README 的诚实边界一致。

放弃的东西：Gradio 的"半小时上线"的速度；React 级别的交互 polish。
如果以后面试官反馈"界面太素"，再升级不迟——先让链接能点。

## 对 eval 的影响

- demo 的 trajectory 展示复用 eval 的 trace 结构；若 demo 里发现 trace 缺字段，
  回过来补 eval_runner 的记录维度。
- 新增回归维度："demo 可跑性"——`web/` 的改动必须保证 DeterministicStub 下
  全链路可走通，不许引入要 key 才跑的节点。
- 部署配置（Dockerfile、spaces README）不进 pytest，但进"发布前检查清单"。
