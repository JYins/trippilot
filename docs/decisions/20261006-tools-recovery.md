## 背景

审查 blocker #9、#10、#11 指出了三个会制造“假成功”的边界：提醒 ID 会在删除后复用，恢复节点会把原调用参数整体丢掉，录制响应又只凭 fixture 名命中而不核对请求。约束是提醒重试不能重复产生副作用，录制模式必须保持确定性，并且现有 12 条 eval 仍要使用离线响应跑通。

## 候选方案

1. 提醒 ID 继续按存量计算，删除时寻找空洞复用；实现短，但 ID 会重新指向另一条提醒，外部引用不可靠。
2. 提醒 ID 使用进程内单调计数器；原型重启后仍会从 1 开始，但单次运行内删除不回退，也不会覆盖存量。
3. 恢复时为每种工具重新拼参数；可以顺手补默认值，但容易再次漏掉业务字段。
4. 恢复时复制原 `ToolCall`，只给明确列出的只读录制工具回退 `fixture`；语义稳定，代价是新增工具需要显式加入白名单。
5. 录制文件只校验 fixture 名；兼容性最好，但无法证明响应属于本次请求。
6. 在录制文件中保存 `expect` 并逐字段精确比较；fixture 要随请求场景增加，不过参数与响应的关系可被测试直接审计。

## 选择

选择 2、4、6。提醒删除时同时移除所有指向该 ID 的幂等映射，因此删除后的同内容调用明确视为新建。恢复保留工具名、来源和完整参数，仅 `map.route`、`map.search`、`weather.now`、`weather.forecast` 可以把调用中已经存在且非默认的 `fixture` 改为 `default`，并在 recovery trace 的 `changes` 中记录字段、旧值和新值。`map_default.json` 校验 `origin/destination`，`weather_default.json` 校验 `area`；`expect` 是请求元数据，成功返回时不暴露给业务结果。

## 为什么

工作日志：先复现了 `len(_store)+1` 在删除第一条后生成 `rmd_0002`、覆盖第二条的路径，因此没有选择找空洞；ID 的含义应是稳定引用，不是当前数组下标。这里仍保留内存原型的边界，进程重启后的全局唯一性要等持久化存储设计时再解决，不能把它包装成永久 ID。

恢复侧先对照失败结果和实际执行调用的顺序，决定从 `tool_calls` 尾部取与 `tool_results` 等长的一段来配对。提醒不允许任何参数回退：模拟“服务端已创建但客户端超时”后，原幂等键原样重试，第二次由工具返回 `duplicate_suppressed`。只有录制型只读查询需要 fixture 失效后的确定性降级，所以白名单没有包含提醒和行程日志。

#11 的取舍是保留 `map_default` 作为“望京到中关村”的真实录制语义，不把 `expect` 改成宽松通配，也不让“国贸/机场/西站”继续借用中关村响应。盘点 eval 后，为不同目的地补各自录制文件并让用例显式选 fixture；中关村用例补齐原本缺失的起点。这样改 fixture/用例的成本更高，但不会为了维持 12/12 而继续接受响应内容和请求不一致。

## 对 eval 的影响

新增 `tests/test_tools_recovery.py`：覆盖删除非末尾提醒后的四次 ID 分配与重建语义、提醒超时恢复时完整参数及幂等键不变、map 恢复只改 fixture 且 trace 留痕，以及 map 的 origin/destination 和 weather 的 area 不匹配时明确失败。现有 eval 中路线目的地不属于中关村的用例改用对应录制 fixture，语义不变；TP-RECOV-001 仍从不存在的 fixture 回退，但其 default 请求改为与默认录制响应一致。全量测试和 12 条 eval 都作为回归项。
