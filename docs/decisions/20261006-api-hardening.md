## 背景

2026-10-06 的代码审查指出 API 入口有三处会让原型表现得比实际能力更可靠。入口把每个调用者都写成已认证的 `owner`，但项目没有认证层；请求日志会留下 `text`、`asr_text` 和策略说明里的个人信息；`asr_confidence` 与 `vehicle_state` 又要等进入图后才校验，错误输入可能变成 500。

这次工作的边界是硬化现有本地原型，不补做一套假的账号系统。车况仍是调用方传入的纯软件模拟状态。

## 候选方案

1. 接入多用户认证并由令牌生成属性：能提供真实身份边界，但当前没有账号、密钥管理和部署基础，仓促加入只会制造另一层未经验证的安全声明。
2. 把入口明确限制为无认证的本地单用户：身份能力与原型现状一致，代价是写操作会被现有 ABAC 当作未认证请求拒绝，记忆也只有一个本地命名空间。
3. 保留 `authenticated=True`，只把用户改名为 `local`：对演示行为影响最小，但字段仍在声称一项不存在的认证事实，因此放弃。

日志方面考虑过先对请求原文做正则脱敏。正则不可能穷举自由文本里的个人信息，漏识别时仍会留下完整原文，所以不把它作为默认路径。请求原文改为只记录字符长度和 SHA-1 前 12 位；这里的摘要只用于关联重复输入，不用于认证或防篡改。12 位比完整摘要更少暴露数据，又足够本地排查短期日志碰撞。响应等确实需要可读上下文的日志继续保留结构，但所有字符串统一遮盖大陆手机号、带标签的生日和中文地址。

请求校验考虑过在端点里手写判断，但 FastAPI 请求模型已经能稳定把约束错误转换为 422，重复判断会产生两套错误格式。因此直接复用 `state.py` 的 `VehicleState`，置信度按概率定义限制在闭区间 `[0, 1]`。

## 选择

API 固定使用 `user_id=local`、`authenticated=False`、`role=local`，并由模块说明和 `/health` 返回 `single_user_local`、`authentication=none`。本地单用户的记忆自然都进入 `local` 命名空间。

请求日志中的 `text` 和 `asr_text` 只保留长度与 SHA-1 短摘要。其他结构化日志经过同一个 PII 脱敏入口；已知敏感键整项遮盖，普通字符串再遮盖手机号、生日和地址。

`TurnRequest.asr_confidence` 使用 `Field(ge=0, le=1)`，`vehicle_state` 使用已有的 `VehicleState` Literal。顺手把 `trip_context` 改为 `default_factory=dict`，避免可变默认值让请求间隔离显得含糊。

## 为什么

首先保证声明与事实一致。无认证入口不能代表某个已认证车主，即使这会让提醒等副作用在当前 API 下被拒绝，也比默认越过 ABAC 更诚实；只读路线和天气仍可运行。下一阶段如果需要恢复多用户写能力，必须先由可信认证层生成 `user_id`、认证状态和角色，再用真实用户 ID 隔离记忆，不能接受客户端自报身份。多用户隔离靠认证层是明确的将来工作，不由当前单用户命名空间冒充。

日志选择“默认不记原文”是因为手机号、生日和地址正则只能降低风险，不能证明自由文本已经安全。短摘要仍可能被低熵输入枚举，因此同时截短且只把它当排查线索；真正需要查看上下文时，统一脱敏函数提供有限的可读性，但不把它宣传为完整 DLP。

在请求边界校验可让客户端错误稳定返回 422，也避免图内 Pydantic 异常被框架当作服务端故障。`0` 和 `1` 是概率的合法边界，超出范围没有业务含义；车辆枚举直接复用状态模型，避免 API 与图各自维护一份字符串列表。

## 对 eval 的影响

新增 `tests/test_api_hardening.py`：验证置信度 `0`、`1` 可接受，`1.5` 和非法车辆状态返回 422；验证 `text`、`asr_text` 在日志中只出现长度与短摘要；验证策略 detail 中的手机号、生日、地址被遮盖；验证 health 和固定属性如实声明本地单用户、无认证。

原有 API 确认协议测试的记忆查询命名空间从 `owner` 改为 `local`，确认和一次性 nonce 语义不变。现有图和 Policy Gate 的独立单元测试仍可显式构造已认证用户，不受本地 API 部署模式影响。
